# SPEC 01 — 任务定义：文本、上下文、媒体、输入条件、歧义类型

> v0.3 | 2026-11-16 | 数值以 `configs/pipeline.yaml` 为准，文中括号里写的是键名。  
> 什么时候读：实现 S4–S5、写提示词、设计评测条件、判断某个样本算不算歧义时。

---

## 1. 符号

| 符号 | 含义 |
|---|---|
| `X` | 目标台词的日语文本，有两种形式（§2） |
| `V` | 视频窗口，无声（§4） |
| `A` | 门控后的音频（§4） |
| `C` | 文本上下文（§3） |
| `Y` | 简体中文译文 |
| `R` | 这句台词的读法集合 `{r1, r2, …}` |
| `r*` | 目标读法：训练目标所表达的读法 |

任务：给定 `X, V, A, C`，生成 `Y`。主方向 Ja→Zh-Hans。

---

## 2. 两种文本形式

语音识别输出的标点不是中性的。句末的“？”是识别模型听了声音之后加的，已经带有语调信息。如果把它留在文本里，再去比较“只给文本”和“文本加音频”，音频的作用就被文本吃掉了。所以每条台词保存两种文本。

| 字段 | 定义 | 用在哪里 |
|---|---|---|
| `text_asr` | 主 ASR 输出，只做基础规范化：去首尾空白，标点统一为全角，连续重复的标点合并为一个 | 生成训练目标；`T_asr` 条件 |
| `text_neutral` | 把 `text_asr` 里的 `text.neutralize_chars`（默认 `？?！!…‥`）每处替换成 `。`，再合并连续的 `。`；其余不变 | 全部分桶判定；模态消融 |

规则：

1. 判断“视频或音频是否改变了译法”的所有条件，文本一律用 `text_neutral`。
2. 训练目标用 `text_asr` 加视频加音频生成，因为这是信息最全的输入。
3. 另跑一个只给 `text_asr` 的纯文本条件。它如果已经能得到目标读法，就给样本打上 `asr_punct_sufficient=yes`，表示“识别出的标点已经够用，级联做法就能解决”。
4. 来源自带人工日语字幕时，人工字幕代替主 ASR 成为 `text_asr`，同样生成 `text_neutral`。

## 3. 上下文策略

| 策略 | 键 | 内容 | 用途 |
|---|---|---|---|
| `C_prev` | `context.policy_prev` | 同一视频内，目标台词之前 `context.prev_window_ms` 内最近的 `context.prev_turns` 句，按时间顺序 | **主策略**，所有条件共用 |
| `C_full` | `context.policy_full` | `C_prev` 再加目标台词之后 `context.next_window_ms` 内最近的 `context.next_turns` 句 | 只用来打 `future_context_sufficient` 标记 |

- 前文各句用 `text_asr`。前文不是被检验的对象，保留它的标点更接近真实使用。
- 说话人标签用片段内的相对编号 `S1`、`S2`……，目标台词的说话人也用这套编号。说话人置信度低于 `context.speaker_tag_min_conf` 时写 `?`。
- 提示词里的格式：

  ```text
  前文：
  [S1] これ、運ぶの手伝おうか？
  当前台词（S2）：いいよ。
  ```

- **为什么要有 `C_full`**：审稿人可能会说“看了后面的台词就知道意思了，不需要视频”。所以对每个候选样本，再用“前文 + 后文”的纯文本条件翻译一次。结果如果已经得到目标读法，就标 `future_context_sufficient=yes`。报告里要同时给出 core 的总数和其中 `future_context_sufficient=no` 的数量，后者记作 `core_strict`。

## 4. 媒体窗口与音频门控

### 4.1 窗口

- 视频窗口 `W_v = [t_start − clip.pre_pad_ms, t_end + clip.post_pad_ms]`，裁到视频边界以内。
- 总长不超过 `clip.max_window_ms`。台词太长时先缩短前面的留白。
- 所有时间都记父视频的绝对毫秒。

### 4.2 每个样本的四个媒体文件

| 文件 | 内容 | 用途 |
|---|---|---|
| `clips_v/<id>.mp4` | `W_v` 的画面，**没有音轨**，H.264，长边不超过 `clip.long_side_px` | 所有带 V 的条件 |
| `audio_gated/<id>.wav` | 和 `W_v` 一样长；只保留 `[t_start − m, t_end + m]` 内的原始声音（`m = clip.audio_gate_margin_ms`），其余置零，边界做 `clip.audio_fade_ms` 的淡入淡出；16 kHz 单声道 | 所有带 A 的条件 |
| `preview/<id>.mp4` | `W_v` 的原始音视频 | 只给人看（QA 预览、抽检页面），不作为主实验的模型输入 |
| `frames/<id>/` | 按 `ocr.fps` 抽的帧，带时间戳 | OCR、线索核验 |

### 4.3 为什么要门控音频

视频窗口比台词长，窗口里的声音会带进别人说的话，特别是台词**之后**对方的回答。这些话不在 `X` 和 `C` 里。如果让模型听到，“音频有用”就可能只是“多听到了几句台词”，不是语调或语气的作用。门控之后，音频里只剩目标台词本身的声音。

画面保留宽窗口，因为动作和反应经常发生在台词前后。这相当于字幕翻译的场景：译者能看到这一小段画面。这个设定写进 `context` 和数据卡。

### 4.4 输入方式

- `T+V`：文本 + `clips_v`。
- `T+A`：文本 + `audio_gated`。
- `T+V+A`：文本 + `clips_v` + `audio_gated`，作为两个独立的媒体项传入（`models.yaml` 里 `teacher.media_input: separate`）。
- 不使用 mp4 内嵌音轨，也不依赖 `use_audio_in_video`。原因有两个：门控更容易保证；ms-swift 有内嵌音频解码挂死的已知问题（见 SPEC 05 §9）。
- P3 M3.1 用资格探针比较“分开传入”和“内嵌音轨”两种方式。如果后者明显更好，由研究者决定是否切换。切换要记入 `decision_log.md`，并且全项目统一。

### 4.5 帧采样

- `video_input.fps`、`video_input.max_frames`、`video_input.max_pixels_per_frame` 在 teacher 的所有调用里保持一致。
- 学生模型可以用另一组设置，但同一个学生的各条件之间必须一致。
- 短手势（半秒左右的摇头、摆手）在低帧率下容易漏掉。P3 M3.1 要比较 2 fps 和 4 fps；线索核验时在线索区间内按 `video_input.verify_fps` 加密。

## 6. 歧义类型（日→中）

类型是多标签。下面的例句都是**虚构的示意，不是数据**，可以用在 `docs/annotation_guideline.md` 和测试夹具里（夹具文件名带 `synthetic`）。

| 类型 | 定义 | 日语里常见的形式 | 中文为什么必须选 | 常见线索 |
|---|---|---|---|---|
| `speech_act` | 同一句话可以是接受、谢绝、道谢、道歉、招呼 | いい（です/よ）、結構です、大丈夫です；どうぞ；失礼します；はい | “好啊”和“不用了”不能并存 | 手势、递接动作、进门或离开；语气 |
| `question_intonation` | 句末没有疑问助词，升调是疑问，降调是陈述 | 行く↗/↘；そうですか↗/↘；〜じゃない↗/↘；〜でしょう↗/↘ | 中文要用“吗/？”或句号 | 句末音高 |
| `polysemy` | 一个词有几个意思，宾语常被省略 | かけて、つけて、切って、消して、取って、落ちた | 中文动词随宾语变：打（电话）/戴上/锁上 | 手里的东西、场景 |
| `ellipsis` | 主语或宾语省略，中文必须补出来 | 来るって言ってた；もう渡した | “他说会来”和“她说会来”要选一个 | 画面里是谁、谁在做 |
| `reference` | 指示词或人称指的是谁、是什么 | あの人、あいつ；それ、あれ | 只有中文必须写出具体所指时才算 | 视线、指向、人物外观 |
| `emotion_prosody` | 语气决定褒贬或真假 | やばい；すごいね；バカ | “糟了”和“太厉害了”相反 | 语气、表情 |
| `speaker_identity` | 谁在说、对谁说 | どうする？ | “你怎么办”和“咱们怎么办”不同 | 画面里的人和朝向 |
| `scene_event` | 画面里发生的事决定词义 | 失礼します（进门/离开）；ついた | “打扰了”和“我先告辞了”不同 | 场景事件 |
| `register_politeness` | 语体和敬语 | です/ます、敬语 | 日语原文通常已经写明，中文按原文选“您/你” | 很少需要视频 |

**方向差异（假设，P4 用数据检验）**：日→中方向，预期 core 主要来自 `speech_act`、`question_intonation`、宾语省略的 `polysemy`、必须补人称的 `ellipsis`，以及褒贬相反的 `emotion_prosody`。`register_politeness` 预期很少，因为礼貌程度已经写在日语原文里；它在中→日方向才重要（P7）。こそあ指示词在中文里常有“这个/那个”这种中性译法，预期多数进 general。

**同音词不算歧义**：ASR 把「ついた」写成「着いた」还是「付いた」属于识别问题。两路 ASR 写法不同的句子会被 C1 挡在 core 之外。用音频纠正识别错误是另一类收益，本版不做，记为 P7 备选。

## 7. 中性译法检验

**定义**：如果有一种自然的中文译法，在所有读法下都算对，这句话就不是“必须二选一”，不能进 core。

**原因**：core 的主指标是“模型有没有选对读法”。如果一个不表态的译文也算对，纯文本模型不看视频也能得分，这条样本就测不出视频的作用。

**示意**（虚构）：

| 日语 | 读法 | 中性译法 | 结论 |
|---|---|---|---|
| すみません | 道歉 / 招呼 | “不好意思”两种都说得通 | 只有这两种读法时不进 core |
| すみません | 道歉 / 道谢 | 道谢要说“谢谢，麻烦你了”，“不好意思”不够 | 可以进 core |
| それ、取って | 盐 / 书 | “把那个递给我” | 不进 core |
| いいよ | 接受 / 谢绝 | 没有 | 可以进 core |
| もう食べた | 我 / 他 | “已经吃了” | 不进 core |
| 来るって言ってた | 他 / 她 | 中文这里不能省主语 | 可以进 core |

**做法**：

1. S9a 的读法归纳提示词（`text_readings`）要求模型回答“有没有中性译法”，并写出来。
2. 读法映射（`reading_map`）有一个 `neutral` 选项。任何一个纯文本候选译文被判为 `neutral`，就说明存在中性译法。
3. 两者任一成立，样本记 `N_NEUTRAL_EXISTS`，进 general。

## 8. 自然最小对

规范化后（去标点、去空白）`text_neutral` 相同、片段不同、core 读法不同的两条样本，组成一个“自然最小对”。它对应“同一句话配不同的场景，译法不同”这个实验。

- 由 S12 自动配对，记在 `labels.contrast.pair_ids`。
- 评测时两条都对才算对（成对准确率）。
- 不为了凑对去伪造样本。对数不够就如实报告。
